# Voltix Dash animation pass

Implemented with UnityMCP in Level01. No packages or commits. The authoritative gameplay
scripts, physics, health, damage, score, movement, attack timings/range, patrol tuning,
camera tuning, level layout and build configuration remain unchanged.

## Implementation

60 new geometric neon frames reuse the existing character and prop SVG designs.
Sprite-only AnimationClips and five reusable Animator Controllers provide crisp states.
The Player has a physics-driven Locomotion blend tree and a separate Action override layer;
Hurt takes priority over Attack, and both return to the current locomotion pose. Accepted
combat events alone trigger attack presentation. Movement-facing updates the sprite, while
an active attack uses its accepted facing direction. No animation event controls gameplay.

PatrolBot reuses Patrol/Death clips and one controller. Its actual gameplay object still dies
immediately. A short-lived visual-only prefab finishes Death without a collider, health,
score, damage or movement component. Existing score remains immediate and guarded once.
A living bot has only Patrol because its existing 1 HP gives it no surviving hurt state.

Environmental clips animate only sprites. Normal Animator time and scaled visual event
windows freeze under pause. No per-frame allocations in the new presentation scripts.
Existing NeonSprite and PlayerFlash materials are reused; no new materials or AudioSources.

## Minimal gameplay-script change

`Assets/Scripts/Enemies/PatrolEnemy.cs`: added only `public int FacingDirection => direction;`.
No patrol logic or serialized tuning changed. This read-only state lets the new child visual
face the authoritative patrol direction. No changes to PlayerMovement, CameraFollow,
PlayerHealth, PlayerCombat, ScoreManager, HazardDamage, EnemyHealth or any other existing script.

## Existing feedback

PlayerFeedback is unchanged. Its existing Player/Visual child receives sprite-only animation;
PlayerFeedback remains the sole owner of additive squash/stretch and the property-block
flash. Existing jump/landing events, camera shake, audio, enemy burst and attack slash remain.
Animator clips contain no transform or color tracks that could overwrite those effects.

## Level01 object changes

- Player: added PlayerAnimationController, referencing existing health/combat/feedback,
  GroundCheck and its existing mask. Player/Visual: added Player Animator and Idle sprite.
- Enemies/PatrolBot, PatrolBot_02, PatrolBot_03, PatrolBot_04: added EnemyAnimationController;
  retained and disabled each root SpriteRenderer; created a local-identity Visual child with
  the copied renderer/material/sorting and PatrolBot Animator. Physics remains on the root.
- Hazards/ElectricBarrier/BarrierField and ElectricBarrier_02/BarrierField: looping sprite
  and ElectricBarrier Animator.
- Hazards/MovingHorizontalHazard/HazardDiamond and MovingHorizontalHazard_02/HazardDiamond:
  looping sprite and MovingHazard Animator.
- LevelObjects/GoalExitPortalVisual: looping portal sprite and GoalPortal Animator.

Four scene objects were created (the bot Visual children); none deleted or repositioned.
All 190 original scene transforms match their pre-task snapshot exactly. Existing collider
types, offsets, trigger states and captured shapes match the snapshot; no collider setters
were used. Collider dimensions/paths and gameplay components were not edited.

## Prefabs

- Created `Assets/Art/Prefabs/PatrolBotDeathVisual.prefab`: SpriteRenderer, Animator and
  EnemyDeathPresentation only; reused NeonSprite material.
- Updated `Assets/Prefabs/Hazards/ElectricBarrier.prefab` at BarrierField.
- Updated `Assets/Prefabs/Hazards/MovingHorizontalHazard.prefab` at HazardDiamond.

These scene objects are not prefab instances, so this adds reusable defaults without adding
extra components to scene objects.

## Testing

- Compiled with Unity 6000.5.6f1 and UnityMCP; no new packages.
- Input-driven checks sampled all eight states: Idle, Run, JumpStart, Rise, Fall, Land,
  Attack, Hurt. All looping environmental frames and all Run/Attack frames were observed.
- A/D facing both ways; stationary J attack left, stationary Left Shift attack right,
  and moving attack right. Visual attack facing matched the accepted event direction.
- Actual damage produced Hurt sprites and the existing property-block flash.
- Input-driven feedback checks retained jump/landing notifications once each, jump scale
  approximately (0.93, 1.09), fall (0.96, 1.06), and landing (1.12, 0.90), additive to sprites.
- Simultaneous accepted Attack and damage selected Action.Hurt / PlayerHurt_00 while
  both parameters were true. A second attack inside the existing cooldown was rejected.
- Enemy death created a visual copy, sampled its Death frames, and removed it. A repeated
  hit inside the existing kill callback left score at exactly 100 and emitted one kill.
- A death visual survived a pause longer than its clip, remained frozen, and cleaned up
  after resume; score stayed 100.
- Falling below the existing threshold respawned at the start, restored HP and reset
  presentation. Three normal 1-damage hits produced HP 2,1,0,3 and one lethal respawn;
  Attack/Hurt parameters and action weight reset to zero/false.
- Pause froze all ten live Animators and sprite frames; resume advanced them again.
  Gameplay audio paused/resumed through the existing AudioListener pause flow.
- Complete automated traversal used existing movement/attack and live physics checks,
  without teleporting, disabling hazards or changing serialized tuning: all 32 platforms,
  four kills/400 score, HP 3/3, zero deaths. Active traversal took 65.28 seconds; the level
  timer including initial setup time displayed 01:10.35. Two mid-level pause/resume checks
  preserved player position, velocity, elapsed timer and Animator progress exactly.
- Goal trigger showed LEVEL COMPLETE / SCORE: 0400 / TIME: 01:10.35 / DEATHS: 0.
  Movement/combat/input stopped, physics stopped safely, presentation returned to Idle,
  timer stayed fixed and Escape did not open conflicting UI.
- Completion Restart button reloaded Level01 with HP 3, score/deaths/timer 0, four bots,
  Idle presentation, Motion 0, Attack/Hurt false, action weight 0 and no leftover death visual.
- Escape -> Resume UI; Escape -> pause Restart UI; Escape -> Main Menu UI -> PLAY UI all
  passed. Each Level01 load had ten Animators, one player animation controller, one score
  manager, one UI document, one listener and the original three audio sources. MainMenu
  had zero gameplay Animators/sources and one UI/listener. No duplicate managers or UI.

The initial test caught an input Send Messages naming collision in the new presentation
script; event handlers were renamed and the full checks were rerun with zero errors.
The first traversal driver missed windows under background editor throttling; its synthetic
input schedule was adjusted, without changing production gameplay or level layout.

Final verification: Unity returned to Edit mode in Level01; Console contains 0 errors.
